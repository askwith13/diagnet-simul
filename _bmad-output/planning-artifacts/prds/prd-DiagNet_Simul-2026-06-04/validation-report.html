Poor

The PRD is technically rich and unusually specific for a hackathon context — the scenario table, tick-level alert sequence for SC-01, FacilityState field list, and NFR targets with measurement hooks are genuine implementation scaffolding. The structural layers (module table, data model, scenario catalogue, risk table) are directly usable for architecture extraction. However, four critical implementation blockers surfaced by the adversarial review push the grade to Poor: the GlobalState data contract is missing from the data model, the node-click → Tab 3 navigation pattern has no specified implementation path, the SHAP stub computation algorithm is named but not defined, and SC-08 "Simulate all" orchestration is unspecified. Any one of these will force developers to make incompatible guesses during the sprint.

Beyond the criticals, the rubric identifies concentrated gaps in done-ness clarity (SC-02–SC-08 have no tick-level specs, making regression tests unwritable), scope honesty (no [ASSUMPTION] tags; kaleido dependency unacknowledged; rpy2 in the stack but deferred), and downstream usability (no FR-NNN IDs, blocking story anchoring). The Week 3 scope — Tabs 2–4, 6 remaining scenarios, export, screenshot, polish — is ambitious for 4 days on a team of 5, and the PRD does not surface this as a risk.

Decision-readiness

Adequate

The PRD surfaces several real trade-offs explicitly: brms/Stan deferred to v2 (R-04), SHAP statistical rigour acknowledged (R-03), Tab 2 performance risk (R-01), and the inter-network sync problem (R-05). Adversarial review — Implementation blockers

review-adversarial.md

The PRD establishes a coherent domain model and workable architecture, but contains four critical implementation-blocking gaps that will force developers to make incompatible guesses during the sprint. The GlobalState data contract is missing; node-click → Tab 3 navigation is technically impossible in standard Streamlit without a workaround; the SHAP stub algorithm is named but not defined; and SC-08 has no orchestration spec. The Week 3 scope (Tabs 2–4, 6 scenarios, export, screenshot, polish) is realistically a 10-day workload compressed into 4 days.

Critical

GlobalState inter-network data contract missing from data model

§4.3, §5.3, §12 R-05
R-05 says "introduce a GlobalState container" but GlobalState appears nowhere in §5. No definition of fields, overflow_delta structure, interface with simulation.py, tick synchronisation rule, or conflict resolution when NET-D is tick 22 and NET-A is tick 18. SC-04 and SC-08 — the two highest-value demo scenarios — are blocked until this is resolved. Two developers will independently invent incompatible schemas.
Fix: Add §5.4 GlobalState specification. Minimum: network_states: Dict[str, NetworkState], inter_network_flows: List[InterNetworkFlow] (typed dataclass with source_net, target_net, patient_count, tick), global_tick: int, overflow_pending: Dict[str, float]. Specify tick-synchronisation rule (synchronous global tick recommended). Specify who calls GlobalState.apply_overflow().
Critical

Node click → Tab 3 navigation has no specified implementation path

§8.5, §8.3
Streamlit ≥1.35 st.tabs() has no programmatic tab-switching API. The standard workaround (JS window.parent.postMessage injection via st.components.v1.html) is non-trivial and undocumented. Tab 3 is the SHAP explainability showcase — the single feature the Funder/Reviewer persona needs to see. If broken or replaced with a clunky workaround, the highest-value demo moment fails.
Fix: Specify the workaround explicitly. Recommended: capture plotly_click event into st.session_state.selected_facility; render Tab 3 content conditionally inside the same page below the tab bar using st.expander — avoids tab-switching problem entirely. Or accept Tab 3 is reached via a selectbox and remove "clicking any node" language.
Critical

SHAP stub computation algorithm not specified

§7, §8.3, §8.5
"SHAP values are approximated from the per_tick_deltas in the scenario YAML" is a name, not an algorithm. No base value, no delta-to-contribution mapping, no normalisation, no handling of facilities not in affected_facilities. SHAP waterfall requires concrete positive/negative bars with numeric values. "Mandatory on every alert" means this gap blocks every alert card's implementation.
Fix: Specify the algorithm. Minimal workable spec: for each field f with non-zero per_tick_delta d_f, shap_f = d_f × weight_f where weight_f is a per-field constant in YAML. Waterfall baseline = facility value at tick 0. Contributions sorted by |shap_f| descending; top 5 displayed. Include a worked numeric example for SC-01 tick 4.
Critical

SC-08 "Simulate all" orchestration unspecified

§6.1 SC-08, §8.4
SC-08 has no start-state definition (post-SC-04 crisis? fresh baseline?), no multi-network YAML delta schema, no definition of "impact metrics," and §8.4 says the "Simulate all" button "runs SC-04" while §6.1 assigns SC-08 to all 5 networks — direct conflict. The primary_network field semantics for "All 5 networks" are undefined.
Fix: Define SC-08 start state (recommended: pre-loaded "post-crisis" YAML baselines, not derived from a prior run). Add multi-network delta schema to §6.3. Define "impact metrics" as specific aggregates (mean composite_bottleneck_score, total patients_queued reduction, count of facilities returning to green). Resolve the §8.4 / §6.1 conflict — clarify that "Simulate all" launches SC-08, SC-04 is accessed via dropdown.
High

Speed slider delta-scaling behaviour ambiguous

§8.2, §6.3
"Controls both tick rate and per-tick state delta magnitude" is ambiguous. Does 4× speed scale deltas (4× delta per tick = different cumulative state) or only animation rate (same state, faster display)? Developer A and Developer B will build incompatible implementations. Alert timings will diverge.
Fix: One sentence in §8.2: "Speed slider controls only the sleep_interval_s between st.rerun() calls. Per-tick delta magnitudes are invariant to speed setting."
High

effective_capacity formula has unit collision and undefined variables

§5.2
min(cartridges / daily_consumption, modules × max_samples_per_module) — both daily_consumption and max_samples_per_module are not FacilityState fields (§5.1). Left term produces days-of-stock; right term produces samples/day. min() across different units is dimensionally incorrect. This feeds predicted_stockout_day, which is a primary Bayesian demo output.
Fix: Rewrite as effective_capacity_days = cartridges / samples_per_module_per_day. Rename the right-hand term to throughput_capacity_samples_per_day = modules × samples_per_module_per_day as a separate metric. Add daily_consumption as an explicit YAML baseline field if consumed-rate tracking is required.
High

Screenshot mode scope and implementation path undefined

§8.6, Tab 4
"Current network map" — is this one Plotly figure or the full 4-tab dashboard? The full dashboard cannot be captured by plotly.io.write_image (single-figure API only). Playwright/Selenium would violate offline constraint. "Current" is ambiguous (running vs. paused).
Fix: "Screenshot exports only the active Plotly network map figure using plotly.io.write_image() with engine='kaleido'." Add kaleido to dependency list. Specify simulation must be paused before screenshot is triggered.
High

Alert message interpolation engine unspecified

§6.3
msg: "DHC queue critical: {patients_queued:.0f} patients" uses f-string syntax in a static YAML string. No spec for: which FacilityState namespace is used, behaviour on missing key (KeyError vs. fallback), whether nested access is supported. A runtime KeyError during a live demo is catastrophic.
Fix: "Message strings interpolated using str.format_map() against FacilityState.__dict__ of the first facility in affected_facilities. Missing keys render as the literal key name in brackets." Provide a safe-format helper in core/models.py.
High

tick_history O(n²) space blowup with immutable state

§5.3, §9 NFRs
tick_history: List[Dict] is stored inside NetworkState. If each tick snapshot includes the full NetworkState (which includes its own tick_history), serialisation is recursive and O(n²). SC-08 at 35 ticks across 5 networks = 164,500 values minimum — with recursive nesting, a RecursionError or multi-second export that kills the Tab 4 demo.
Fix: Specify in §5.3: "Each tick_history entry is a flat dict: {tick: int, facility_id: str, **facility_state_fields}. The tick_history list is excluded from NetworkState serialisation snapshots to prevent recursive growth."
Medium

Pulsing ring animation technically incompatible with Streamlit rerun model

§8.3
Plotly does not support per-frame opacity oscillation without rebuilding the entire figure per frame. At 1.2 Hz this conflicts with the 400ms tick render budget and the st.rerun() loop. Developer will either skip it silently or waste sprint time before abandoning.
Fix: Downgrade: "Critical nodes display a static outer ring at 1.5× node radius in the critical colour with 0.4 opacity. Pulsing animation deferred to v2.0."
Medium

Scenario comparison requires two scenario run histories with no state isolation spec

§8.6, Tab 4
No spec for whether comparison is post-hoc or concurrent, how session_state stores two independent tick_history streams, or which scenario "owns" the top bar controls during comparison. Developer will invent the architecture from scratch.
Fix: "Scenario comparison is post-hoc only. After any scenario completes, its tick_history is saved to st.session_state.scenario_snapshots[scenario_id]. Tab 4 compares any two saved snapshots. No simultaneous dual-run required."
Medium

Alert panel persistence, deduplication, and scoping rules absent

§8.3
No spec for: whether alerts persist across ticks or expire, deduplication on re-trigger, per-network vs. global scope, or what displays at tick 0. In SC-08 across 5 networks, hundreds of alerts could fire — "14 most recent" semantics become critical but undefined.
Fix: Add to §8.3: "Alert panel shows 14 most recent AlertRecords from NetworkState.alerts for the currently selected network. Alerts persist for the lifetime of the current scenario run. Same-tick duplicate alerts (same type + same facility) are deduplicated. At tick 0: 'No alerts — simulation not started.'"
Medium

"Simulate all" button conflicts with SC-04 assignment

§8.4 vs. §6.1
§8.4 says the button "runs SC-04." §6.1 defines SC-08 as the all-networks scenario. Two developers will implement different behaviours.
Fix: Decide and state: "The 'Simulate all' button launches SC-08. SC-04 is accessed via scenario dropdown and always runs on NET-D as primary network."
Medium

M3 → M4 dependency chain is architecturally inconsistent

§7
M3 produces 128-dim node embeddings as "input to M4," but M4 uses Dijkstra path-finding on edge weights — not node embeddings. NetworkX node2vec is not a standard library; the node2vec Python package is not in the stack. If M4 silently falls back to plain Dijkstra, the Q-table and M3 claims are misleading.
Fix: Decouple M3 from M4. Specify M4 uses Dijkstra with composite edge weights (travel_time + tat_penalty) and a pre-loaded Q-table YAML lookup — no M3 dependency. Label M3 as v2 placeholder.
Low

Inter-network link YAML schema absent

§4.3, §11.1
§11.1 shows intra-network links; inter-network connections (NET-A↔NET-C etc.) have no YAML representation. graph.py cannot build a cross-network graph from the config as specified.
Fix: Add top-level inter_network_links key to §11.1: - source: NET-D, target: NET-A, source_facility: DHC-D, target_facility: DHC-A, travel_time_min: 240, flow_type: overflow.
Low

WCAG AA alert card colours will fail as specified

§9, §8.3
#ef4444 (red) on white = ~4.0:1 contrast ratio (fails WCAG AA for normal text). #f59e0b (amber) on white = ~2.8:1 (fails even for large text). PRD explicitly mandates WCAG AA for alert cards — the colour values given will not meet this NFR.
Fix: Add colour spec table to §9: CRITICAL = #dc2626 background with white text (4.5:1); DTO ADVISORY = amber card (#f59e0b) with dark text #92400e (7.3:1); BAYESIAN = #1d4ed8 with white text (5.9:1).
Low

Reset button behaviour during active run unspecified

§8.2
No spec for: whether Reset stops the sim before clearing state, whether tick_history is preserved for export, whether selected_facility is cleared. Clearing tick_history on Reset blocks the data-team Tab 4 export use case.
Fix: Add to §8.2: "Reset preserves tick_history in scenario_snapshots[scenario_id] for export. Simulation halted (is_running = False) before state clear. selected_facility cleared."
Low

Tab 2 caching strategy specified as st.cache_data — incorrect mechanism

§9, §12 R-01
R-01 mitigation says "offload graph computation to background thread via st.cache_data." st.cache_data is a memoisation decorator, not a threading mechanism. Background threads in Streamlit require threading.Thread or concurrent.futures, neither of which is thread-safe with st.session_state.
Fix: "betweenness centrality and PageRank computed once per tick per network, cached in st.session_state.graph_cache[network_id][tick] (plain dict). Tab 2 mini-maps render from cache, not recomputed per rerun."
